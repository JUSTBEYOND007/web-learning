### 技术实现角度

**Q：你说的虚拟列表是怎么实现的？为什么能提升性能？**  
- 我自己封装了一个 `useVirtualList` Hook（`src/hooks/useVirtualList.ts`），本质是**只渲染视口附近的那一小段数据**，其他数据用一个占位高度“假装存在”。  
- 做法是：根据 `scrollTop`、`itemHeight` 和 `containerHeight` 算出当前应该展示的起止索引 `startIndex/endIndex`，只对这段数据做 `map` 渲染，并通过 `transform: translateY(offsetY)` 把它们挪到正确位置。  
- 相比一次性渲染 1000 条 DOM，我们实际只渲染几十条，**大幅减少 DOM 数量、diff 成本和布局/绘制开销**，列表滚动就会明显更流畅。

---

**Q：`useVirtualList` Hook 具体做了什么？**  
- 入参：`items`（完整列表）和 `{ itemHeight, containerHeight, buffer }`。  
- 内部用 `useState` 维护 `scrollTop`，根据它计算：
  - `visibleCount = ceil(containerHeight / itemHeight)`  
  - `startIndex` / `endIndex`（加上 `buffer` 缓冲区，避免边缘空白）  
  - `visibleItems = items.slice(startIndex, endIndex + 1)`  
  - `offsetY = startIndex * itemHeight`  
- 返回：`containerRef`、`visibleItems`、`totalHeight`、`offsetY`、`handleScroll`。  
- 组件里只渲染 `visibleItems`，外面套一个高度为 `totalHeight` 的容器，再用 `translateY(offsetY)` 做偏移。

---

**Q：如何计算滚动视窗与元素位置关系？**  
- 滚动视窗的“窗口”高度是 `containerHeight`，每行固定高度 `itemHeight`：  
  - 当前滚动到哪一行：`scrollTop / itemHeight` → 取整就是逻辑上的起点行  
  - 为了避免频繁切换，用 `buffer` 向上/向下多预渲染几行  
- 所以关系是：  
  \[
  startIndex = \max\left(0, \left\lfloor \frac{scrollTop}{itemHeight} \right\rfloor - buffer\right)
  \]  
  \[
  endIndex = \min(items.length - 1,\ startIndex + visibleCount + 2*buffer)
  \]

---

**Q：如何保证列表滚动时不卡顿？**  
- **控制渲染数量**：始终只渲染几十个 DOM 节点（`visibleItems.length`），滚动距离多大都不会线性增加。  
- `handleScroll` 用 `useCallback` 包装，内部只更新一个简单的 `scrollTop` 状态，不做复杂计算或副作用。  
- 渲染区域用 `transform: translateY`，这是 GPU 友好的属性，避免频繁触发布局重排。  
- 审批列表页面数据量是 1000 条，在这种策略下滚动非常顺畅，没有明显掉帧。

---

### 性能优化角度

**Q：大数据量场景下，你是如何控制渲染数量的？**  
- 通过 `useVirtualList` 把“**渲染数量 ≈ 视口可见条数 + buffer**”控制在一个固定范围，比如视口能看到 10 条，我只渲染 10 + 2*5 = 20 条。  
- 不管列表有 100 条还是 10k 条，**同时挂在 DOM 树上的节点数都在几十级别**，这保证了渲染性能。

---

**Q：和普通 map 渲染有什么区别？为什么普通渲染会性能差？**  
- 普通写法是：`items.map(...)`，数据有多少条 DOM 就有多少个节点，数据达到几千条后：
  - 首次渲染会很慢，JS diff + DOM 创建成本很高  
  - 滚动时浏览器要对大量节点做布局、绘制，容易掉帧  
- 虚拟列表只让 React 关心“当前需要显示的那几十条”，其余由 `totalHeight` + `translateY` 伪装位置，**把 O(N) 的 DOM 数量压缩到 O(1)**。

---

**Q：有没有遇到过跳帧或滚动抖动问题？如何解决？**  
- 在这个 Demo 里用的是**固定高度行**，不需要动态测量，所以不会出现高度误差导致的跳动。  
- 如果真实业务里存在行高不一致，我会：  
  - 要么在设计上约束为固定高度（简单粗暴，最稳）  
  - 要么做一层高度缓存 + 累积高度表，在 `scrollTop`→index 的映射上做二分查找，这属于进阶实现。当前 POC 版本选择了固定高度方案，简单且稳定。

---

### React Hooks & 设计模式角度

**Q：为什么封装成 Hook？为什么不是直接写组件？**  
- 虚拟列表是一个**功能模式**，不仅可以给审批列表用，将来也可以给日志列表、消息列表用。  
- 封装成 Hook（`useVirtualList`）好处是：
  - UI 层完全可定制：业务组件自己决定用 `List`、`Table` 还是自定义 DOM  
  - 逻辑复用：滚动计算、索引计算全部集中在 Hook 内  
  - 更符合 React Hooks 的“UI = f(state)”理念，视图只是 `visibleItems` 的一个投影。

---

**Q：状态管理、ref、scroll 事件的处理方式？**  
- **状态**：用 `useState` 只存一个 `scrollTop`，其他全部是“派生状态”（`startIndex/endIndex/visibleItems/offsetY`）。  
- **ref**：`containerRef` 返回给调用方，用在滚动容器上，必要时可以用它控制滚动位置或做测量。  
- **scroll 事件**：用 `handleScroll` 绑定到容器的 `onScroll`，内部只读 `e.currentTarget.scrollTop`，然后 `setScrollTop`，没有额外副作用，避免阻塞主线程。

---

**Q：你是怎么处理元素高度不一致的情况？**  
- 在当前项目里，审批项是设计为**固定高度 100px** 的，这样虚拟列表实现可以非常简洁、稳定。  
- 面试可以如实说：  
  - “这个 Demo 场景下我通过视觉设计统一了行高，虚拟列表按固定高度实现。”  
  - “如果将来要支持不等高，我会引入高度缓存 + 累积高度表，或使用成熟库（如 react-window 的 variable size 列表）来处理，这属于下一阶段的优化方向。”
