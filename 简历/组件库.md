### 第一板块：架构与工程化（必问）

**Q1. 为什么要使用 Monorepo（pnpm workspace）架构？解决了什么问题？**
*   **简历关联**：简历提到“采用 Monorepo 架构进行多包管理”。
*   **回答思路**：
    1.  **代码复用**：组件库（`packages/components`）、文档（`packages/docs`）、工具函数（`packages/utils`）都在一个仓库，本地调试非常方便，不需要 `npm link`。
    2.  **依赖管理**：`pnpm` 的幽灵依赖（Phantom Dependencies）解决机制，以及 `workspace` 协议可以保证依赖版本一致，减少磁盘占用。
    3.  **统一规范**：统一配置 ESlint、Prettier、TSConfig，避免不同子项目风格不一致。

**Q2. 你的组件库是如何实现“按需引入”和“Tree-shaking”的？**
*   **简历关联**：简历提到“支持按需引入和全量引入”。
*   **回答思路**（参考 PDF 1 第8页）：
    1.  **ESM 模块**：构建时输出 ES Module 格式（`.mjs` 或 `type: module`），这是 Tree-shaking 的基础。
    2.  **Side Effects**：在 `package.json` 中配置 `"sideEffects": false`（或者指定样式文件有副作用），告诉打包工具（Webpack/Vite）哪些文件没有副作用可以安全移除。
    3.  **导出策略**：
        *   **全量**：`export * from './components'`。
        *   **按需**：用户 `import { Button } from 'aurora-ui'` 时，构建工具分析依赖图，只打包 Button 及其依赖。
    4.  **样式处理**：如果是 SCSS，可能需要配合 `vite-plugin-style-import` 或者让用户手动引入样式，或者像 Antd v5 一样使用 CSS-in-JS 实现动态按需加载样式。

**Q3. 构建工具为什么选择 Vite 而不是 Webpack？**
*   **简历关联**：简历技术栈写了 Vite。
*   **回答思路**：
    1.  **开发体验**：Vite 基于 ESM 的冷启动极快，热更新（HMR）速度与项目规模无关，开发组件库时响应迅速。
    2.  **库模式（Library Mode）**：Vite 原生支持库模式打包，配置 `build.lib` 即可轻松输出 ESM、CJS、UMD 格式。
    3.  **对比**：Webpack 配置繁琐，构建速度慢，虽然生态更成熟，但对于现代组件库开发，Vite 足够且更高效。

### 第二板块：组件实现细节（核心考察）

**Q4. 你在简历中提到了 `Upload` 组件，它是如何实现的？有哪些难点？**
*   **简历关联**：简历提到“实现了 Upload、Message 等组件”。
*   **回答思路**（参考 PDF 1 第3页）：
    1.  **核心结构**：原生 `<input type="file" style="display:none" />` 配合 `useRef` 触发点击。
    2.  **文件获取**：监听 `onChange` 事件获取 `e.target.files`，或者通过 `onDrop` 获取拖拽文件。
    3.  **难点/亮点**：
        *   **进度条**：使用 `axios` 的 `onUploadProgress` 或 `XMLHttpRequest` 计算进度。
        *   **生命周期管理**：封装 `useUpload` Hook，管理文件列表状态（Uploading, Success, Error）。
        *   **预览**：使用 `URL.createObjectURL(file)` 生成本地预览地址，记得组件卸载时 `URL.revokeObjectURL` 释放内存。

**Q5. 你提到了 Message（全局提示）组件，这种“函数式调用”的组件是怎么实现的？**
*   **简历关联**：简历提到 `Message` 组件。
*   **回答思路**：
    1.  **不同点**：普通组件写在 JSX 里，Message 是 `Message.success('text')` 调用。
    2.  **实现原理**：
        *   创建一个独立的 DOM 容器（`document.createElement('div')`）挂载到 `body` 上。
        *   使用 `React.createRoot` (React 18) 或 `ReactDOM.render` 将 Message 组件渲染到这个容器中。
        *   **单例模式**：维护一个全局的实例列表，确保新消息推入列表，旧消息定时移除（SetTimeout）。
    3.  **过渡动画**：配合 `framer-motion` 或 CSS Transition 实现消息滑入滑出的效果。

**Q6. 关于 Input 组件，你是如何处理“受控”与“非受控”模式的？**
*   **参考资料**：PDF 1 第9-12页详细讲了 Input。
*   **回答思路**：
    1.  **受控（Controlled）**：`value` + `onChange`，状态由父组件管理。
    2.  **非受控（Uncontrolled）**：`defaultValue` + `ref`，组件内部维护 state。
    3.  **最佳实践**：可以使用 `useMergedState`（类似 `rc-util` 中的实现）来统一管理 `value`（受控）和 `defaultValue`（非受控）的优先级，确保组件既能受控使用也能非受控使用。
    4.  **组合模式**：像 Antd 一样，通过 `Input.TextArea`、`Input.Password` 挂载子组件，利用 `Compound Component` 模式导出。

### 第三板块：文档与插件（简历亮点）

**Q7. 简历中提到“设计 Preview 插件实现源码预览与高亮”，具体是怎么做的？**
*   **简历关联**：这是一个很具体的亮点。
*   **回答思路**：
    1.  **痛点**：在 Storybook 或文档中，不仅要展示组件 UI，还要展示这段 UI 对应的源代码。
    2.  **实现**：

        *   **高亮**：使用 `highlight.js` 或 `prism.js` 对源码字符串进行语法着色。

**Q8. Storybook 在你的项目中起到了什么作用？如何自动生成文档？**
*   **简历关联**：简历提到 Storybook。
*   **回答思路**：
    1.  **开发环境**：它是组件的“实验室”，可以在隔离环境中开发组件，不用启动整个业务项目。
    2.  **文档生成**：利用 `storybook-addon-docs` 和 JSDoc 注释（TypeScript Interface 注释），自动提取 Props 表格（ArgsTable），减少手动编写文档的工作量。

### 第四板块：测试与质量保证

**Q9. 你的组件库是如何做单元测试的？Jest 测试了哪些场景？**
*   **简历关联**：简历提到 Jest 和测试覆盖率。
*   **回答思路**（参考 PDF 1 第3-6页）：
    1.  **工具**：Jest + React Testing Library。
    2.  **测试分层**：（基础逻辑测试 边界情况测试 快照测试）
        *   **快照测试 (Snapshot)**：保证 UI 结构不被意外修改（render 后 matchSnapshot）。
        *   **逻辑测试**：比如 `Counter` 组件点击加号，值是否 +1。
        *   **事件测试**：`fireEvent.click` 模拟点击，检查 `onClick` 回调是否被调用（`toHaveBeenCalled`）。
    3.  **边界测试**：传入空数据、超长文本、非法格式时，组件是否崩溃。

如果面试官问：“**Storybook 在你的项目中起到了什么作用？它是如何自动生成文档的？**”，请按以下三个层次回答。

#### 第一层：它解决了什么问题？（宏观作用）

> **话术**：“在开发组件库时，Storybook 对我主要起到了两个核心作用：
> 
> 第一是**独立开发环境（Sandbox）**。因为组件库是跟业务解耦的，我不需要启动庞大的业务项目（BizFlow）来调试一个小小的 Button。Storybook 提供了一个干净的沙箱，让我能专注于组件本身的 UI 和交互逻辑，极大地提升了开发效率。
> 
> 第二是**可视化的文档平台**。它不仅是给开发者看的说明书，更是组件的‘展示柜’。通过 Storybook，团队成员可以直观地看到组件长什么样，有哪些属性可以配置，而且是可以实时交互的。”

#### 第二问：它是如何自动生成的？（核心原理 - 必背）

这里不需要去背 Webpack/Vite 的复杂配置，只需要抓住 **TypeScript + 注释** 这个核心点。

> **话术**：“关于自动生成文档，我主要利用了 Storybook 强大的**类型推断**能力，具体流程是这样的：
> 
> 1. **基于 TypeScript 接口**：我在写组件时，会非常规范地定义 interface Props。比如 Button 组件，我会定义 type, size, disabled 等属性的类型。
>     
> 2. **JSDoc 注释**：在这些 Interface 上方，我会写上标准的 JSDoc 注释（/** ... */）。比如在 disabled 属性上注释‘是否禁用按钮’。
>     
> 3. **自动解析**：Storybook 内置了（或配置了）react-docgen-typescript 这样的工具。它会自动扫描我的组件文件，解析 TS 类型定义和注释，自动在文档页生成一个 **Props Table（属性表）**。
>     
> 4. **结果**：这样我就不用手写文档表格了，代码改了，文档自动更新，保证了文档和代码的一致性。”
