### 面试回答策略：RBAC 权限控制方案

**面试官问：** “我看你简历里提到了动态权限控制，具体是怎么实现的？是如何结合路由懒加载的？”

**你的回答范本：**

“在 BizFlow 这样复杂的 SaaS 平台中，我设计了一套基于 **RBAC（基于角色的访问控制）** 模型的动态路由方案。主要分三个层面来实现：

**第一层：路由守卫与高阶组件（的核心逻辑）**  
我没有选择在每个页面内部判断权限，而是封装了一个 **高阶组件（HOC）** AuthWrapper。  
它接收 roles 数组作为参数，从 **Zustand** 全局 Store 中获取当前用户的角色信息。  
如果权限匹配，渲染子路由组件；如果不匹配，则自动重定向到 403 页面。这种方式实现了**关注点分离**，业务页面不需要关心权限逻辑。

**第二层：动态路由与懒加载结合**  
结合 React Router v6，我在路由配置表中，将业务组件通过 React.lazy 进行懒加载，并包裹在 AuthWrapper 中。  
为了防止懒加载过程中的网络抖动导致应用崩溃，我在外层包裹了 **Error Boundary** 和 Suspense，确保加载失败时用户能看到友好的提示，而不是白屏。

**第三层：用户体验优化（亮点）**  
除了基础拦截，我还做了两个体验优化：

1. **预加载策略**：当用户鼠标 Hover 到导航菜单时，利用 动态 import 提前加载目标路由的 Chunk，减少点击后的等待时间。
    
2. **持久化与防篡改**：权限数据虽然存在 Zustand 里，但也同步到了 localStorage 并配合 Token 刷新机制，防止用户刷新页面后登录态或权限丢失。”

### 问题：如何定位瓶颈？（关注工具与指标）

**核心逻辑：** 别只说感觉慢，要说用了**Lighthouse**打分，用了**Network**看体积，用了**Bundle Analyzer**看包结构。

**🗣️ 参考回答：**  
“我是分三步来定位的：

1. **宏观分析**：首先使用 Chrome 的 **Lighthouse** 跑了一下评分，发现 Performance 分数很低，且提示 **LCP（最大内容绘制）** 时间过长（3.7s）。
    
2. **微观定位**：我打开 DevTools 的 **Network 面板**，发现首屏加载了一个巨大的 JS 文件（index.js），体积超过了 2MB，下载耗时很久，阻塞了页面的渲染。
    
3. **可视化分析**：为了搞清楚这个 JS 为什么这么大，我使用了 webpack-bundle-analyzer 插件，生成了依赖图谱。我发现 node_modules 里的 React、Ant Design、Echarts 等第三方库全都被打包进了同一个文件里，这就是导致体积过大的元凶。”

> **关键词记背：** Lighthouse（看分）、Network（看加载时长）、webpack-bundle-analyzer（看包体积结构）。


我在项目中选择 pnpm 主要原因：

1. **极快的安装速度与磁盘空间节省（核心原理）**：  
    pnpm 使用了 **Content-addressable store（基于内容的存储）**。不同项目如果依赖同一个版本的包（比如 React），在磁盘上只会存储一份物理文件。pnpm 会通过 **硬链接（Hard link）** 将项目中的 node_modules 指向这个全局存储。这不仅大大减少了磁盘占用（这对 Monorepo 这种依赖巨大的架构很重要），也让 pnpm install 速度极快。
    
2. **彻底解决了‘幽灵依赖’问题（安全性）**：  
    以前用 npm/yarn 时，采用了扁平化（Hoisting）结构，导致我可以非法访问到即使在 package.json 里没声明的依赖（这就是幽灵依赖）。  
    pnpm 默认采用 **非扁平化的 node_modules 结构**，通过 **软链接（Symbolic link）** 组织依赖。只有显式声明的包才能被访问，这在多人协作的大型项目中，极大地保证了依赖管理的安全性，避免了‘明明本地能跑，上线却报错’的问题。
