**SSE 与 WebSocket 的核心区别及 AI 对话场景的选择理由**

SSE（Server-Sent Events）与 WebSocket 主要有三个本质区别：

1. **通信方向**：SSE 是单向的（服务端→客户端），WebSocket 是双向全双工通信
2. **协议基础**：SSE 基于 HTTP 协议，WebSocket 需要协议升级（HTTP → WS）
3. **连接复杂度**：SSE 自动重连且实现简单，WebSocket 需要手动管理连接生命周期
	```
	WebSocket 是全双工通信协议，  
	浏览器只负责建立连接，不会自动重连。  
	如果连接断开，需要开发者在 onclose 或 onerror 中  
	手动实现重连逻辑，并管理连接生命周期。
	```
```
WebSocket 适用于需要实时双向通信的场景，例如：
1. 即时聊天系统
2. 在线协同编辑
3. 在线游戏
4. 实时数据推送（如股票行情）
5. 实时通知系统
因为 WebSocket 建立的是长连接，并支持全双工通信，
服务器和客户端都可以主动发送消息，延迟较低，
所以非常适合实时应用场景。
```


**AI 对话场景多采用 SSE 的四大原因：**
		(关键词：*用户提问 持续推送 AI 生成的文本流    客户端无需频繁发送数据)
1. **单向推送完美契合**：用户提问后只需服务端持续推送 AI 生成的文本流，客户端无需频繁发送数据，SSE 的单向特性恰好满足这一需求 
2. **实现成本低**：基于标准 HTTP 协议，无需处理复杂的协议升级和心跳保活，开发调试更简单
3. **防火墙友好**：使用标准 HTTP/HTTPS 端口，不会被企业防火墙拦截（WebSocket 常被限制）
4. **天然断线重连**：浏览器原生支持自动重连，网络抖动时无需额外处理


**封装 EventSourcePolyfill 支持自定义头部鉴权"的完整实现解析**

这个项目的核心难点在于：**原生 `EventSource` API 不支持自定义请求头**，而 AI 对话场景必须在每次 SSE 连接时携带用户的 `Authorization` token 进行鉴权。项目通过 `EventSourcePolyfill` 库 + Zustand 状态管理完美解决了这个问题。
![[Pasted image 20260228155853.png]]

```ts
import { EventSourcePolyfill } from 'event-source-polyfill'
import { useUserStore } from '@pc/store'
 
// 建立sse连接
export const createSSE = (chatId: string) => {
  const { token } = useUserStore.getState()  // 1. 从 Zustand store 获取最新 token
  return new EventSourcePolyfill(`${BASE_URL}/chat/getChat/${chatId}`, {
    headers: {
      Authorization: token || ''  // 2. 将 token 注入请求头
    }
  })
}
```

**为什么 SSE 连接必须携带 token 鉴权？**

**A:**

主要原因是**安全性**，具体包括：

1. **防止未授权访问** - 只有持有有效 token 的用户才能建立连接
2. **数据隔离** - 不同用户的消息不能混在一起
3. **防止会话劫持** - 恶意用户无法窃取他人的会话
4. **个性化服务** - 服务器根据用户身份返回相应内容
5. **计费和限额** - 根据用户等级提供不同服务
6. **合规性要求** - 满足数据保护法规的审计要求


打字机效果：
关键词（*流式推送小块文本  高频率状态更新触发 React 重渲染**）
**核心原理：逐字符追加 + 高频率状态更新触发 React 重渲染**

### **实现原理的三个关键步骤**

#### **1. *服务端流式推送小块文本（chunk）**

后端不是一次性返回完整响应，而是按字符或词组持续推送：

```js
服务端推送流：
data: {"type":"chunk","content":"你"}
data: {"type":"chunk","content":"好"}
data: {"type":"chunk","content":"，"}
data: {"type":"chunk","content":"我"}
data: {"type":"chunk","content":"是"}
data: {"type":"chunk","content":"AI"}
data: {"type":"chunk","content":"助手"}
data: {"type":"complete","content":"你好，我是AI助手"}
```

每个 `chunk` 通常是 1-3 个字符，推送频率可能是 **每 50-100ms 一次**。

---

#### **2. 前端接收 chunk 后立即追加到状态（高频更新）**

在 AIRichInput/index.tsx#L351-L356L351-L356 中：

```js
eventSourceRef.current.onmessage = (event) => {  const data = JSON.parse(event.data)  if (data.type === 'chunk') {    addChunkMessage(data.content)  // 每收到一个 chunk 就立即更新状态  }}
```

**关键点：每次收到 chunk 都会触发一次状态更新**

---

#### **3. Zustand 状态更新触发 React 重渲染（打字机视觉效果）**

在 useChatStore.ts#L40-L87L40-L87 中：

```js
addChunkMessage: (chunk: string) => {  const { selectedId } = useConversationStore.getState()  set((state) => {    const currentMessages = [...(state.messages.get(selectedId as string) || [])]    const lastMessage = currentMessages[currentMessages.length - 1]     if (lastMessage && lastMessage.role === 'system') {      // 找到最后一条系统消息的文本内容      const lastContent = [...lastMessage.content]      const lastTextContent = lastContent[lastContent.length - 1]       if (lastTextContent && lastTextContent.type === 'text') {        // 关键：字符串拼接，每次追加新的 chunk        lastContent[lastContent.length - 1] = {          ...lastTextContent,          content: lastTextContent.content + chunk  // "你" → "你好" → "你好，" → ...        }      }       // 不可变更新，触发 React 重渲染      currentMessages[currentMessages.length - 1] = {        ...lastMessage,        content: lastContent      }    } else {      // 第一个 chunk 时，创建新的系统消息      currentMessages.push({        content: [{ type: 'text', content: chunk }],        role: 'system'      })    }     const newMessages = new Map(state.messages)    newMessages.set(selectedId as string, currentMessages)    return { messages: newMessages }  })}
```

**核心逻辑：**

- 每次收到 chunk，就把它**拼接**到最后一条系统消息的 `content` 字符串末尾
- 通过不可变更新（是指不直接修改原对象，而是创建新对象/数组进行更新创建新对象）触发 React 的 diff 算法
- React 检测到 `messages` 变化，自动重新渲染消息列表
- 用户看到的效果：文字一个个"蹦"出来
